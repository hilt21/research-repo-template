# Research Template 需求对齐

状态：需求与 Repository Spec v0.1 已获整体确认，正在实施；完成情况见 acceptance.md。

依据：[开源项目调研方案](https://chatgpt.com/share/6a9be367-ba34-83ee-912f-5695bee00592)，于 2026-09-05 读取。

## 用户此前明确确认

- 首先探索供 Agent 辅助学习、研究与知识沉淀的 template 仓库，开发应用不是首要目标。
- 优先级：Agent 能理解并继续工作 → 知识形成结构 → 研究可复现、审计和继续 → 持续研究体验 → 长期 Knowledge OS。
- 一个课题一个仓库，先小范围推进。
- Topic、Entity、Relation、Event、Claim、Source、Task、Artifact 可作为起始对象集合，但需要持续探索迭代。
- Agent 支持搜索、研究、知识维护；自主运行层先定义接口。
- 保留 Research Trace。
- 接受 Markdown 主体与结构化 metadata 的人机接口。
- Task 驱动知识变化先作为实验，不预先认定其必要性。
- 偏好的入口是自由对话后触发知识沉淀。

## 原调研方案建议清单

- Research / Trace / Knowledge 的分层边界与知识进入长期状态的条件。
- OKF v0.2 兼容扩展及最小对象字段。
- Claim 的核心地位、Relation 按需对象化、Source 记录与原始材料的分层。
- 短研究可不建 Task；长研究使用 Task 作为持续执行载体。
- Knowledge Diff、人工审阅、校验与 Git 提交之间的协议。
- 目录结构、四个 Agent Skills、Python 工具与具体依赖。
- 首版是否包含真实研究示例、确定性校验与跨会话恢复验证。

以上用于追踪原方案建议，具体确认进展以“本轮已确认”为准。开源项目的活跃度尚未在本轮独立核验；OKF 协议的核对结果见下文。

## 本轮已确认

### 首版交付范围

用户确认：复制模板后，能与 Agent 完成一轮真实研究、沉淀可追溯知识，并在新会话中继续研究。

交付包含：

- 仓库结构、对象模板与使用说明。
- 研究、知识沉淀、查询、维护四个 Skill。
- 一个独立的完整示例，展示证据、研究轨迹、知识变更与研究输出。
- 支撑这条闭环的最少校验工具。

整体需求仍在对齐中，此项确认不等于开始实现。

### 首个真实验收课题

用户确认采用“汽车 EMB 执行器架构及其向铁路场景迁移的限制”。示例先围绕一个收窄的研究问题展开；后续已确认报告范围与验收场景，具体首轮问题在规格第 10.2 节提出，已随规格整体确认。

该课题将用于检验多来源引用、事实与推断的区分，以及新证据出现后对已有判断的更新。

### Agent 支持范围

用户确认首版以 Codex 为主要使用和实测入口，完整验收研究、知识沉淀及新会话恢复。核心协议、Markdown 文件和 Skill 内容保持可迁移；Claude Code、OpenCode 的专用适配与实测放到后续。

### 知识正式入库边界

用户确认：以用户确认后的 Git 提交作为知识正式入库的边界。

知识沉淀流程：

1. Agent 整理研究轨迹与来源，在工作区生成候选知识变更。
2. 自动校验，并展示新增、修改、冲突及证据不足的判断。
3. 用户审阅并可要求修改；确认后 Agent 才执行 Git 提交。

工作区中的候选知识变更尚未正式入库。本地研究轨迹的保存时机与随知识入库纳入版本历史的方式已另行确认。

### 研究轨迹保存

用户确认：Agent 可以在完成一批资料阅读、形成阶段性发现或准备切换任务等关键节点，主动保存本地研究轨迹。

记录包含当前问题、已查来源、暂定发现、证据缺口和下一步，以支持新会话接续。这些保存不自动执行 Git 提交，也不代表知识正式入库；正式知识继续遵循人工审阅确认的入库流程，关联研究轨迹随该次入库一并提交。

### Task 使用门槛

用户确认采用“短研究只保存 Trace，需要持续跟踪时再建 Task”的规则。

- 单轮问答或小范围资料比较：保存研究轨迹即可。
- 明确需要跨会话推进、有待办事项或遇到阻塞的研究：Agent 主动创建 Task，记录研究目标、完成标准、当前状态和关联轨迹。

示例：“解释一种 EMB 传动机构”可以只有 Trace；“比较三类架构并评估铁路迁移限制”适合建立 Task。Task 的价值继续通过真实使用验证。

### 知识入库的证据门槛

用户确认：尚无外部证据的研究假设可以经人工审阅后入库。入库代表值得长期保存，不代表已经证实。

- 有证据支持的判断：关联来源及具体证据位置。
- 待验证假设：明确标注为假设，记录提出依据、关联研究轨迹和待验证事项，不能当作已有事实引用。

### 冲突证据与判断更新

用户确认：新证据与已入库判断冲突时，Agent 先检查是否由适用条件不同导致，例如汽车与铁路、实验样机与实际运行。

若仍无法解释，候选知识变更应保留原判断及支持证据、新证据及其挑战的具体部分、尚待核实的问题与下一步。经用户审阅确认后，再将判断标记为“存在争议”，或修订其适用范围。

### 来源记录与原始材料

用户确认采用“来源记录入库，全文快照保存在本地”的默认方式。

- 随知识入库：标题、作者或发布机构、链接、获取时间、具体引用位置；有快照时记录其内容哈希。
- 本地缓存：网页全文、PDF 等原始材料默认不进入 Git。
- 随仓库共享的原始材料：单独明确纳入范围。

用户接受仓库轻量与原文跨设备可用性之间的取舍：换电脑后部分原文需要重新获取，本地快照不会自动跟随。此处保留的是已读取版本的快照；重新获取的版本是否一致需要核对，不能假定外部来源永远可重新取得。

### Claim 粒度

用户确认：“需要独立引用、验证或更新的关键判断”单独保存为 Claim。每条 Claim 表达一个可判断的命题，并写清适用条件、证据和状态。

机构的基本介绍可以放在 Entity 条目中，多种架构的综合比较可以放在研究报告中。该粒度用于支持关键判断的独立质疑和更新，同时控制文件数量。

### Artifact 与知识条目的关系

用户确认：报告、图表、演示文稿等 Artifact 是基于知识生成的研究输出；影响结论的关键判断应能追溯到 Claim。

写报告时产生的新判断可以先作为草稿保留，再走知识入库流程。已有 Claim 更新后，关联报告标记为“待复核”，由 Agent 按需修订。

### 校验阻断与提示边界

用户确认采用“结构错误阻止入库，研究中的不确定性作为提示保留”的规则。

- 阻止入库：ID 重复、必填字段缺失、内部引用失效，以及标为“有证据支持”的 Claim 缺少来源或定位信息。
- 提示但允许审阅后入库：待验证假设、存在争议的判断、尚未使用的来源、待复核的报告。
- 由 Agent 和用户进行语义审阅：证据是否真正支持判断、推断是否合理、适用条件是否充分。

自动检查负责结构与引用完整性。

### 协议基线

用户确认采用“OKF v0.2 知识文件格式＋本项目的研究约定”：知识文件遵循 OKF 的格式、来源和文档生命周期约定；假设、支持、争议等研究状态使用独立扩展字段；Task、Trace、人工审阅和严格入库检查由本项目定义。

### 降低使用者心智负担

用户要求从系统设计哲学角度审视如何降低使用者的心智负担，并确认“自然语言意图作为默认入口，Agent 管理结构，用户集中审阅知识变化”作为首版交互原则。

日常使用应围绕研究、继续、整理与输出展开。对象分类、文件命名、引用关联和结构检查由 Agent 与工具承担；用户关注研究目的、实质取舍和一轮知识变化的接受。四个 Skill 保留为内部职责及可选显式入口。保存状态、假设、争议、适用条件与证据缺口保持可见。

设计说明与体验验收建议见 [低心智负担设计草案](./low-cognitive-load-design.md)。该原则不改变此前已确认的入库审阅边界；恢复范围与默认版本保存方式见下文，实现契约已在规格草案中收敛，已随规格整体确认。

### 研究进度的版本保存与恢复范围

用户确认：本轮相关的 Trace、Task 随知识入库一起提交到 Git。

- 研究过程中自动保存本地进度，同一仓库的新会话可以继续。
- 知识入库时，一份审阅摘要同时覆盖知识变化及关联研究轨迹、任务进度；用户确认后一起提交。
- 尚未提交的进度，首版只保证在原工作副本中恢复；跨设备接续需要先保存到版本历史并同步。原始材料快照仍遵循默认本地缓存的规则，Git 同步不代表快照已同步。

日常默认保留一次集中审阅。Git 提交中的研究进度记录不因此转化为正式知识判断。

### Entity、Event、Relation 按需建模

用户确认：这三类对象有实际研究价值时才独立建条目。

- Entity：技术、机构或概念需要持续描述、反复引用时建立。
- Event：某次发生的事情及其时间对研究判断有意义时建立。
- Relation：普通关系使用链接和文字表达；需要单独维护有效期、属性或证据时，再建立关系条目。

模板提供这些能力，由 Agent 按需使用。每轮研究以知识是否可追溯、可继续为验收重点，不要求对象类型齐全。

### 工具依赖与运行方式

用户确认首版采用 Codex、Git 与少量 Python 本地工具：Codex 负责研究、知识整理和调用工具；Python 与 uv 承担确定性操作及运行环境、依赖管理；Markdown 与 Git 保存知识和历史。数据库、常驻服务、专用 Agent Runtime、MCP Server 和 Web UI 留待后续。

使用者完成一次环境初始化，日常由 Agent 调用工具。具体 Python 版本和最小依赖在规格与实现阶段确定。

### 确定性执行与 Agent 思考的边界

用户明确要求：确定性流程用脚本执行，需要思考的行动由 Agent 执行。

据此拆分职责：

- 脚本：按明确规则解析和检查字段、分配及检查 ID、计算哈希、解析引用、生成可机械推导的索引或关联清单，以及执行已获授权的版本操作并报告实际结果。
- Agent：理解研究问题、制定检索方向、评估证据、区分冲突与适用条件差异、组织知识、提出变更，以及撰写和修订研究输出。
- 人：研究目标与实质取舍，以及对具体知识变更的审阅接受。

同一行动可拆分为 Agent 的语义决定与脚本的确定性步骤。例如，Agent 判断 Claim 应如何修订，脚本根据显式引用找出受影响输出；输出内容如何修改仍由 Agent 判断。脚本不能判定证据是否真正支持 Claim，Agent 不能用口头断言替代必须执行的校验。

工具输出需要反映真实成功或失败，不能把脚本失败解释为检查已通过；既有人工审阅与提交规则保持有效。上述职责是架构约束，首版只实现已确认研究闭环实际需要的脚本。

### 首版 EMB 示例与验收

用户确认以下验收闭环：

1. 完成一轮真实研究，产出带来源、适用条件和证据缺口的 Markdown 架构对比报告。
2. 审阅入库后保留一个后续 Task，在全新会话中仅凭仓库记录恢复并继续。
3. 补充证据后更新相关判断，识别并复核受影响报告；不预设真实资料一定存在冲突。
4. 用明确标注的测试样例验证结构错误会阻止入库，假设与争议可以按规则保留。

首版研究输出以 Markdown 报告、表格和必要示意图为范围。真实研究材料与行为测试样例需要区分，测试样例不充当研究证据。

### 仓库交付与公开范围

用户确认首版交付为私有 GitHub Template 仓库，包含完整模板、四个 Skill、校验工具、使用文档和独立 EMB 示例，供真实使用与迭代。待协议和使用体验稳定后，再决定公开发布及面向外部使用者的维护承诺。

用户确认仓库名称与归属为 hilt21/research-repo-template。GitHub 连接器当前登录账号已核对为 hilt21；名称可用性与创建权限将在实际创建前检查，尚未创建远端仓库。

### 文档语言

用户确认采用“中文为主，协议标识用英文”：使用说明、研究内容、审阅摘要和 EMB 示例以中文编写；目录、字段、命令和对象类型用英文，关键术语首次出现时中英对照。首版维护一套中文文档，后续公开时再考虑英文版。

## 协议核对事实

2026-09-05 核对 [OKF 官方规范](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)：页面版本为 0.2，允许扩展字段；其 status 表达文档生命周期。OKF 消费端必须容忍缺少可选字段与失效链接，因此本项目已确认的严格入库检查需要明确为项目规则，不能宣称是 OKF 自身的拒绝条件。

协议基线已获用户确认，具体兼容目录边界和字段契约仍需在规格中定义。知识入库审批与对照来源核验内容需区分，不能仅因同意保存假设就自动声称已完成事实核验。
