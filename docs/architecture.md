# 架构与边界

一个研究实例围绕一个课题持续积累知识，按需要组织阶段性交付。用户表达目的、反馈和实质取舍；Agent 组织研究并判断语义；脚本执行确定性操作。深模块与减轻用户负担是首要设计约束。

## 信息如何流动

```text
原始材料 / Chat / 口述
        ↓ 保留出处与实际取得的版本
Source + Research Trace
        ↓ 提出候选判断 → 脚本检查 → 用户审阅 → 受控 Git 提交
共享 Knowledge
        ↓ 按用途引用
Deliverable → Task → Artifact → 用户反馈与修订
```

写作中产生的新判断回到候选审阅流程。交付完成与知识接受是两个决定；假设可以被接受保存，但不会因此成为已证实事实。

## 文件各自承担什么

| 落点 | 职责 |
| --- | --- |
| `research.yaml` | 实例配置；模板未初始化，初始化后只有一个 Topic |
| `knowledge/` | OKF v0.2 知识包，含 Topic、Source、Claim 和按需创建的 Entity、Event、Relation |
| `traces/` | 精选研究过程与可选交接入口，不等于完整 Chat |
| `tasks/` | 需要持续跟踪的行动与下一步 |
| `deliverables/` | 交付目标、受众、范围与完成标准；共享知识，不复制独立 Wiki |
| `artifacts/` | 实际产出，重要判断引用 Claim |
| `.cache/` | 本地原文快照和审阅凭据，默认不随 Git 同步 |
| `tests/` | 合成验证材料，与实例知识隔离 |

精确字段和必需章节以 [Schema](../schemas/objects.yaml) 为准，术语以 [CONTEXT](../CONTEXT.md) 为准。文档生命周期、判断状态、任务进度、交付完成和输出复核分别表达，不共用一个“完成”标记。

## 小接口隐藏维护工作

用户无需决定文件命名、引用格式或检查顺序。四个 Skill 分别负责研究、查询、维护和集中入库，共同引用一份 [工作流](workflow.md)。

工具通过 `new` 创建记录，`status --target` 集中提供指定工作的导航与材料状态，`check` 检查结构，`prepare/accept` 约束实际审阅范围。依赖指纹由同一套逻辑比较，调用方无需重新实现目录扫描和哈希规则。

相关性选择、冲突解释、报告写作和整体论证复核由 Agent 完成。只有影响下一步且不能自行消解的歧义才询问用户；无关坏草稿不应阻断有效工作的恢复。

## 保存、接受与恢复

本地保存支持同一工作副本接续，不自动入库。用户审阅具体知识变化后，受控提交绑定所选文件、内容和 Git 基线；审阅后内容或基线变化，需要重新准备。Trace 随提交保存，仍是过程记录。

Chat → Codex Work 使用项目上下文、短交接摘要和可定位的原始会话。摘要说明当前决定、排除事项、假设和下一步，不增加授权。导航顺序不构成无条件权威排序，也不能控制产品是否已将历史全文注入上下文。

来源记录描述出处；原始材料不自动等于事实。本地快照的内容哈希用于核对实际版本，换设备后缓存可能不可用。依赖指纹未变只表示字节未变，不表示论证正确；更新指纹前必须完成相应语义复核。

## 有意保留的边界

- 知识包格式与本项目的严格审阅规则分开；项目拒绝入库不等于通用 OKF 文件不合法。
- 脚本检查显式结构与依赖，不判断证据真实性、隐含语义关系或远端链接可访问性。
- 用户直接操作 Git 可以绕过协议；确认参数是 Agent 已取得用户确认的声明，不是身份认证。
- 不提供常驻服务、数据库、调度引擎或跨设备原文打包；真实 Codex Work 验收状态见 [验证指南](validation.md)。
