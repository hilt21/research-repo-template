# 降低使用者心智负担：设计草案

状态：交互原则与具体实施规格均已确认。本文保留设计依据，实际验收见 acceptance.md。

## 设计判断

已有的对象、来源、状态和校验约定用于保障可追溯性。若要求使用者记住它们、决定文件归属并手动维护关系，会把系统的组织成本转移给研究者。首版应围绕研究意图提供交互，将结构管理分配给 Agent，将可确定的检查分配给工具。

降低心智负担需要同时减少：启动时要学的概念、过程中要做的机械决策、恢复时要回忆的上下文、审阅时要辨别的变化，以及使用者对保存和入库状态的不确定感。

## 建议原则

1. 意图作为入口。使用者可以表达“研究这个问题”“继续上次研究”“整理这一轮”；Agent 选择相应 Skill，承担 Task 创建、对象分类、文件命名、引用关联和校验。四个 Skill 是内部职责划分，显式命令可以保留为可选入口。
2. 按需展示细节。恢复时提供简短研究入口：当前问题、已知结论、关键不确定性和下一步。常规操作可沿入口完成；对象、来源和轨迹细节可以继续追查。首版使用 Markdown 和 Agent 回复承载，无需新增应用界面。
3. 明示保存与接受的区别。用自然语言报告“研究进度已保存”“本轮整理待确认”“本轮知识已入库”；这些是进度摘要，不替代内部状态或暗示不同文件不能处在不同阶段。只有保存实际成功后才能报告已保存。
4. 围绕语义集中审阅。每轮提供一份有边界的变更摘要，说明新增或修订的判断、主要依据、争议及受影响输出，允许查看具体证据和文件差异。用户确认针对所展示的这批内容；实质修改后应更新摘要再审阅。
5. 内容不确定性保持可见。减少字段和操作术语的暴露，但保留假设、争议、适用条件和证据缺口。入库确认不等于事实核验；自动修好结构也不代表判断成立。
6. 维护由使用过程触发。Agent 优先处理当前研究涉及的结构问题和关联输出；可选维护 Skill 支持更全面的检查。不要把每条普通提示都扩展为用户待办，遇到影响方向或证据解释的选择再请求用户判断。
7. 恢复依靠仓库记录。新会话读取正式知识和已保存研究进度，识别候选变更并说明其尚未入库的状态。上下文不足时指出具体缺口；本地原文缺失时不能声称已重新核验来源。

## 建议的责任划分

| 使用者 | Agent | 确定性工具 |
| --- | --- | --- |
| 研究目的与优先级 | 检索、比较和提出候选判断 | 字段、ID 和引用检查 |
| 实质性的范围与取舍 | 组织对象、维护轨迹与任务 | 按明确规则执行文件及版本操作 |
| 审阅本轮知识变化 | 汇总依据、冲突与受影响输出 | 提交前验证及结果反馈 |

Agent 对语义工作的判断仍需可追溯且允许纠正。工具不获得扩大研究范围或替用户接受知识的权限。

用户进一步确认的执行约束：确定性流程使用脚本，需要思考的行动由 Agent 执行。混合行动应拆分，例如脚本沿显式引用定位受影响输出，Agent 判断输出内容如何修订；需要实际执行的检查必须留下真实结果。

## 建议加入验收的体验要求

- 从模板开始到完成首轮入库，使用者无需学习对象类型或手写 YAML。
- 新会话中表达“继续上次研究”，Agent 能指出当前问题、已知与待验证判断、未完成工作及候选变更，并给出可执行的下一步。
- 常规入库只需审阅一份有依据的语义摘要；格式修复不产生逐字段确认请求，关键证据可进一步检查。
- 能分别识别本地进度保存成功和正式入库成功；失败或未完成时不会报告成功。
- 出现反证时，用户能理解哪个判断受影响、为什么，以及关联输出需要什么复核。

上述为后续规格化使用的验收建议，尚无实现或实测结果。具体 Skill 发现与调用方式需在 Codex 中实际验证。
