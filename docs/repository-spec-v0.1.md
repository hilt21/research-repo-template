# Research Repository Template — Repository Spec v0.1

状态：2026-09-05 已获用户整体确认，作为首版实施基线。实际完成情况见 acceptance.md。

本文收敛 [需求访谈记录](./requirements-alignment.md)、[领域术语](../CONTEXT.md) 与 [低心智负担设计](./low-cognitive-load-design.md)。标记为“设计建议”的部分用于将共识落实为可实现契约，随本文一并审阅，尚不视为此前已经单独确认。

## 1. 目标与交付

创建私有 GitHub Template 仓库 `hilt21/research-repo-template`。一个由模板创建的研究实例围绕一个课题，使用 Codex 持续研究、保留进度、沉淀可追溯知识并生成输出。

首版交付：

- 可初始化的模板结构、对象模板、中文说明、领域术语与关键决策记录。
- research、commit-knowledge、query-knowledge、maintain-knowledge 四个 Skill。
- Python 本地工具与 uv 环境配置，执行确定性操作。
- 独立的 EMB 真实研究示例，包括来源记录、轨迹、关键判断、后续任务、Markdown 报告、表格与必要示意图。
- 结构校验测试与真实使用验收记录。

使用说明、研究内容、审阅摘要和示例以中文为主；目录、字段、命令及对象类型使用英文，关键术语首次出现时中英对照。首版维护一套中文文档。

暂缓：数据库、常驻服务、专用 Agent Runtime、MCP Server、Web UI、其他 Agent 的专用适配及实测。公开发布、开源许可与对外维护承诺在后续公开阶段决定。

## 2. 系统设计约束

1. **按意图使用。** 用户表达研究、继续、整理或生成输出的目的；Agent 负责选择 Skill 和组织文件。
2. **确定性流程交给脚本。** 字段、ID、哈希、显式引用与授权后的版本操作必须实际执行并报告结果。
3. **需要思考的行动交给 Agent。** 研究范围、证据解释、判断修订和报告写作需要语义工作。
4. **知识接受交给人。** 候选变更经过校验与集中审阅，用户确认后才提交入库。
5. **文件承载持久状态。** 长期知识使用 Markdown 与 YAML 元数据；Git 提供历史。索引只能从文件重建。
6. **进度、知识、输出各有边界。** Trace 记录研究过程，知识条目承载长期判断，Artifact 组织研究成果。
7. **入库不代表证实。** 假设与争议可以入库，但状态、适用条件和证据缺口保持可见。
8. **按需建模。** 不要求每轮研究生成全部对象类型；Task 只用于需要持续跟踪的研究。
9. **反馈真实。** 保存、校验或提交失败时不得报告成功；源材料无法取得时不得声称完成核验。
10. **控制使用成本。** 常规使用无需用户编辑元数据、学习对象类型或逐项批准格式修复。

## 3. 目录与协议边界（设计建议）

```text
research-repo-template/
├── README.md
├── AGENTS.md
├── CONTEXT.md
├── research.yaml
├── pyproject.toml
├── uv.lock
├── .gitignore
├── .agents/skills/
│   ├── research/SKILL.md
│   ├── commit-knowledge/SKILL.md
│   ├── query-knowledge/SKILL.md
│   └── maintain-knowledge/SKILL.md
├── knowledge/                    # 单个 OKF 知识包
│   ├── index.md
│   ├── topic.md                  # 初始化课题时生成
│   ├── sources/                  # Source 记录，不放全文快照
│   ├── entities/
│   ├── claims/
│   ├── events/
│   └── relations/
├── traces/                       # 研究轨迹与本轮审阅摘要
├── tasks/                        # 持续跟踪的研究工作
├── artifacts/                    # 报告、表格、必要示意图
├── templates/                    # 对象模板，不作为当前课题知识读取
├── schemas/                      # 项目字段契约
├── scripts/                      # 确定性操作
├── tests/                        # 标明用途的测试样例
├── docs/                         # 协议、使用说明、ADR、验收记录
├── examples/emb/                 # 独立研究实例，复用根目录工具与 Skill
│   ├── research.yaml
│   ├── knowledge/
│   ├── traces/
│   ├── tasks/
│   └── artifacts/
└── .cache/sources/               # 本地材料快照，默认 Git 忽略
```

根目录供新课题初始化，EMB 示例保持隔离；工具明确针对一个研究实例运行，不递归将示例和测试样例混入当前课题。副本带有示例不等于支持多课题知识平台。

`knowledge/` 是 OKF 兼容范围。将来源记录也放入该范围，使 Claim 能直接引用包内来源；原始材料仍单独缓存。`README.md`、Skill、Trace、Task 和 Artifact 文件属于项目工作协议，不宣称整个仓库都是一个 OKF 包。包内链接及保留文件遵循 [OKF v0.2 规范](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)。

Skill 使用 `.agents/skills/` 保存单份定义；这是当前 [Codex 官方文档](https://developers.openai.com/codex/skills/) 列出的仓库发现位置。自然语言触发与同名全局 Skill 的干扰需实测，不仅检查文件存在。

`research.yaml` 只保存实例配置：协议版本、初始化状态、课题文件位置与语言。未初始化模板可以为空；初始化后的研究实例必须有且仅有一个 Topic。不会在模板根目录预装 EMB 判断。

## 4. 最小对象契约（设计建议）

以下是 v0.1 的逻辑字段契约。元数据只保留校验、检索和关联所需内容；解释、证据摘述与研究问题正文保留为 Markdown。

### 4.1 公共约定

- 知识条目使用 `type`、`title`、显式 `status`，按适用性使用 OKF 来源与生成记录。
- 项目新增字段放入 `research` 命名空间，包含稳定的 `id`；Trace、Task、Artifact 也使用同一实例内的稳定 ID 约定。
- 稳定 ID 由脚本分配，重命名文件时保留；它是项目标识，不替代 OKF 自身的路径身份约定。
- `status` 保留文档生命周期含义；`research.claim_state`、`research.task_state` 等分别表达研究状态。
- 项目字段中的文件路径相对于研究实例根目录；OKF 字段与 Markdown 包内链接按 OKF 规则解析。校验器必须区分这两种基准。
- 未知来源属性如作者、发布日期允许明确标为未知，不能为满足字段校验编造内容。
- `generated` 记录实际生成者及时间；`verified` 只用于实际对照来源进行的内容核验。允许保存假设的审阅确认不自动填写为事实核验。

### 4.2 对象最小内容

| 对象 | 元数据及关联 | Markdown 必需内容或条件 |
| --- | --- | --- |
| Topic | 稳定 ID | 研究问题、范围、预期完成标准 |
| Source | 原始出处、获取时间；已取得快照时记录路径与哈希 | 标题、作者或发布机构信息及其未知项说明；材料获取与可用性说明 |
| Claim | `claim_state`、来源与引用定位、关联 Trace | 单一关键命题、适用条件、提出依据；假设需有待验证事项，争议需列出双方证据及待核实问题 |
| Entity | 稳定 ID；按需关联来源和 Claim | 对象的简要描述，影响研究结论的关键判断链接到 Claim |
| Event | 发生时间或已知时间范围；来源 | 发生了什么及其与课题的关系，保留时间精度 |
| Relation | 两端 Entity、关系名称、需独立维护的属性；相关来源或 Claim | 关系描述及有效条件；普通链接无需生成该对象 |
| Task | `task_state`、关联 Trace | 目标、完成标准、进度、下一步；阻塞时说明阻塞原因 |
| ResearchTrace | 保存时间、关联 Task（可选）、检查过的来源、候选变更路径 | 问题、检索与阅读记录、暂定发现、采纳或排除证据的简要理由、缺口、下一步 |
| Artifact | `review_state`、所依赖的 Claim ID | 研究输出正文或输出文件引用；草稿中的新增关键判断应明确标注 |

建议状态集合：Claim 为 `hypothesis / supported / contested / rejected`；Task 为 `open / active / blocked / done`；Artifact 为 `draft / current / needs_review`。拒绝某条判断的理由和证据继续保留。状态变更按已确认的审阅规则执行。

Artifact 的 `current` 仅表示对所引用知识版本已完成复核；受支持程度仍取决于所引用 Claim，不能解读为结论已证实。

### 4.3 证据关联

Claim 的来源指向 Source 记录。逐项证据需要定位信息，如页码、章节、段落锚点或可识别的材料片段；网页没有页码时不虚构页码。

建议每条证据记录 `source_id`、`locator` 和 `role`（`supports / challenges / context`），并与 OKF 来源引用对应。脚本检查引用存在和字段齐全，Agent 判断证据角色是否成立。`supported` 至少需要一条完整的支持证据；`hypothesis` 可以暂时没有外部来源，但必须保留提出依据、Trace 与待验证事项。

材料重新获取时保存新版本及其哈希，不静默覆盖此前已引用的快照。缺少本地缓存是可用性提示；已存在缓存与记录哈希不匹配则是需要处理的完整性错误。

## 5. 自然语言入口与四个 Skill

| 用户意图 | Skill | 主要产出 | 完成边界 |
| --- | --- | --- | --- |
| 研究问题、补充证据、继续研究 | research | 轨迹、来源候选、按需创建或更新 Task | 实际进度已保存，未完成项明确 |
| 整理这一轮、沉淀知识 | commit-knowledge | 候选知识变化、校验结果、集中审阅摘要 | 用户确认后的对应内容提交成功 |
| 查询现有结论与依据 | query-knowledge | 带状态和依据的回答 | 区分已入库知识、假设、争议和本地候选内容 |
| 检查过时内容、整理关联问题 | maintain-knowledge | 结构修复、待复核清单、语义修订建议 | 格式修复可执行，知识修订进入审阅流程 |

生成报告由 research 承担，已有输出的复核由 maintain-knowledge 承担，不新增第五个 Skill。各 Skill 说明适用条件、输入、输出、必需脚本及失败处理。显式 Skill 名可保留，日常不要求用户记忆命令。

维护优先处理当前研究涉及的对象。结构性修复不能擅自改变判断含义；无法唯一确定正确引用时交由 Agent 判断，不能为通过检查随意补链接。

## 6. 研究与入库协议

1. **恢复。** 读取实例配置、知识索引、相关 Task、最近 Trace 和 Git 工作区状态；呈现当前问题、已知、关键不确定性及下一步。
2. **研究。** Agent 查阅已有知识并开展检索、阅读与分析。按需创建 Task；在关键节点保存可观察研究轨迹。
3. **准备变更。** Agent 在工作区组织候选知识、关联来源与报告，并生成本轮语义摘要。
4. **执行检查。** 脚本检查候选内容、引用和受影响输出；Agent 处理可修复项及语义问题。
5. **集中审阅。** 用户看到新增与修订的判断、依据、争议、受影响输出及关联 Trace、Task；可以展开证据或文件差异，也可以要求修改。
6. **提交。** 用户确认后，脚本再次验证实际待提交内容与审阅范围一致，提交该批内容。实质变化后必须更新摘要并重新审阅，不顺带提交无关工作。
7. **反馈。** 成功时报告本轮知识已入库及版本标识；失败则保留工作并指出具体问题，不伪装成成功。

一次确认覆盖本轮知识及其关联进度。Trace 中的暂定发现，即使随提交保存，也不会自动成为知识条目。

知识更新允许保留假设、争议和被推翻的判断。发现冲突先检查适用条件，再提出争议状态或适用范围修订；未解释清楚的冲突不被悄悄消除。

## 7. Knowledge Diff 审阅内容（设计建议）

每轮摘要记录在对应 Trace 的“本轮知识变化”部分，避免额外引入一个必须维护的顶层知识对象。

摘要包含：

- 本轮研究问题和简短结论。
- 新增、修订或弃用的对象；关键判断的变化前后及理由。
- 支持与挑战证据、待验证事项。
- 受影响的输出，以及其已复核或待复核状态。
- 本轮提交范围内的 Trace、Task 和文件清单。
- 脚本校验结果及仍存在的提示。

脚本可以生成文件清单、类型计数和引用影响范围；语义摘要由 Agent 撰写。自然语言确认针对这份具体摘要和对应变更，脚本不声称能自行证明用户已作出内容判断。

## 8. 确定性工具范围（设计建议）

首版提供以下操作，具体脚本拆分以最少实现为准：

| 操作 | 输入与结果 | 不承担的语义职责 |
| --- | --- | --- |
| 初始化与 ID 分配 | 确认的课题信息 → 初始化文件、唯一 ID | 不替用户选择研究目标 |
| 结构与引用校验 | 明确实例及候选文件版本 → 错误、提示、退出结果 | 不判断证据真实性或推断有效性 |
| 哈希与索引 | 材料内容或条目元数据 → 哈希、可重建索引 | 不把索引内容当作新判断 |
| 影响定位 | 变更 Claim 与显式依赖 → 需复核的 Artifact | 不决定报告应如何改写 |
| 受控提交 | 已审阅的文件范围 → 校验、Git 提交结果 | 不替用户批准入库 |

校验规则来自 `schemas/` 和明确的跨对象约束，避免在 Skill、脚本和文档各维护一套相互冲突的字段定义。依赖数量以正确解析 YAML、Markdown 和校验契约的实际需要为限，不预设 CLI 框架或插件机制。

检查与提交针对同一批实际内容，不能只检查工作区然后提交另一份暂存内容。脚本错误要有可定位信息；Agent 可以修复输入或实现问题，但必须重新运行检查。

本地工具及 Skill 是约定的执行入口；首版不承诺在用户直接绕过工具操作 Git 时仍提供不可绕过的安全强制机制。

## 9. 保存、恢复与输出复核

本地保存不自动提交。未提交进度的恢复范围为原工作副本；已提交并同步的文件支持跨设备接续，忽略的原始材料快照需另行获取。

恢复时结合 Git 中已接受的知识版本和工作区差异，明确哪些是候选修改。无法取得可靠基线时说明缺口，不默认为候选知识已经接受。恢复只读取仓库保存的轨迹与说明，不依赖上一会话的隐藏上下文。

研究入口按需呈现“当前问题、已知、关键不确定性、下一步”，并链接到条目和轨迹。默认不添加需要人工维护的第二份状态数据库或重复知识摘要文件。

影响复核建议：在处理本轮 Claim 实质变更时，脚本沿显式依赖找到关联输出并置为 `needs_review`，将该变化纳入候选变更。Agent 复核输出后才更新为 `current`。复核脚本不将报告自动改写为新结论，也不能发现没有显式记录的全部语义依赖。

## 10. 校验规则与验收

### 10.1 结构行为

| 场景 | 预期 |
| --- | --- |
| ID 重复、必填字段缺失、内部引用失效 | 阻止对应候选入库，定位文件与问题 |
| `supported` 缺少来源或定位信息 | 阻止入库 |
| 无外部来源的 `hypothesis`，但依据、轨迹及待验证事项完整 | 提示并允许审阅后入库 |
| 信息完整的 `contested`、未使用来源、待复核报告 | 提示并允许审阅后入库 |
| 初始模板无研究条目 | 模板结构检查通过；初始化后执行实例规则 |
| 本地缓存缺失 | 提示无法本地核对原文，不伪造核验结果 |
| 已有缓存哈希不匹配 | 报告完整性错误，处理后重新检查 |
| 实际待提交内容不同于被检查和审阅的内容 | 不提交，重新准备与审阅 |
| 提交或保存失败 | 保留可恢复内容，明确报告失败 |

负向测试使用明确标注的测试样例，与真实研究知识隔离；不能把测试构造的冲突当作 EMB 领域事实。

### 10.2 真实 EMB 闭环

主题为“汽车 EMB 执行器架构及其向铁路场景迁移的限制”。具体候选架构随可取得的真实资料确定，不预先填充技术结论。首轮围绕可比较的架构、适用条件及迁移证据缺口形成报告。

首轮研究问题建议收敛为：“哪些汽车 EMB 执行器架构具有可追溯的公开描述，其向铁路应用迁移时有哪些适用条件与尚待验证的问题？”该表述随本文整体审阅。

必须留下以下验收证据：

1. 初始化并完成首轮研究，报告中的关键判断能追溯到 Claim 和来源定位。
2. 本轮内容经审阅提交，保留有目标、完成标准和下一步的后续 Task。
3. 在独立新会话中仅凭该研究实例记录，恢复问题、已有判断、待验证事项和后续工作并继续推进；仅在原会话复述总结不算通过。
4. 新来源促成相关判断更新，脚本找出受影响报告，Agent 完成复核或明确保留待复核状态。不要求真实资料必然互相矛盾。
5. 全程可用自然语言表达意图，用户无需手写 YAML；审阅能直接看到判断及依据。

验收记录列出实际环境、执行结果和证据位置。无法实际完成的新会话测试保持未通过，不以脚本模拟记录或理论推演冒充。自然语言 Skill 路由需真实验证，其他 Agent 或操作系统不因文件可移植而自动获得“已实测”声明。

## 11. 实施顺序
