# Research Repository Template

**面向 Codex 的研究仓库模板，把对话中的线索整理成有出处、可审阅、可接续的研究成果。**

像一本会交接的研究笔记本：你说明想研究什么、查看产出并给出反馈；Codex 整理材料、记录决定与下一步，你接受值得长期保留的知识变化。

[先看交接案例](#先看一个交接案例) · [开始自己的研究](#开始自己的研究) · [了解设计](docs/architecture.md)

## 让下一次研究，从上一次的决定继续

研究一旦跨越多轮对话，资料、假设和决定就容易混在一起：哪句话有证据？哪个方案已经否定？这次报告要给谁看？下次应该继续什么？

这个模板把这些信息保存在同一个课题仓库中：

- **继续有入口。** 简短交接记录当前目标、决定、排除事项和下一步，原始会话可按定位回查。
- **判断有出处。** 关键判断保留来源、适用条件与假设或争议状态，写进报告不自动成为事实。
- **产出有目标。** 同一份研究可支持不同受众的报告与分享，各自保留范围和完成标准。

日常用自然语言表达意图，文件命名、引用组织和结构检查由 Agent 与工具承担。

## 先看一个交接案例

仓库自带一个可查看、可运行检查的**合成案例**，故意保留历史噪声和样稿错误：

> 助手曾建议把“节能 20%”当作已证明的结论，并改成采购建议。
>
> 用户随后明确：20% 只是未验证假设，不讨论采购与成本，改成面向非专业同事的 10 分钟分享，先给样稿。

以上为原文的简述。继续这项工作时，关键是恢复后一个决定，并识别样稿仍在重复的过度结论。

| 查看什么 | 你能检查什么 |
| --- | --- |
| [七轮原始会话](tests/fixtures/work/raw-chat.txt) | 哪些是助手提议，哪些是用户明确接受或否定的内容 |
| [简短交接](tests/fixtures/work/traces/current.md#交接入口) | 当前范围、排除事项、假设和下一步是否被保留下来 |
| [分享目标](tests/fixtures/work/deliverables/talk.md)与[研究报告目标](tests/fixtures/work/deliverables/report.md) | 如何共享知识，同时保持不同受众与完成标准 |
| [故意有错的样稿](tests/fixtures/work/artifacts/talk.md) | 为什么结构检查通过，仍需要 Agent 审阅论证 |

在 Codex 中打开仓库后，可以直接复制这段话：

```text
只读查看 tests/fixtures/work 合成实例，继续 tasks/talk.md 对应的工作。
说明当前目标、已经否定的方案、仍待验证的判断，以及样稿中需要复核的具体内容。
按需回查原始会话，记录实际读取的材料，不修改测试文件。
```

这是可复现的测试材料与预期行为，不是真实研究成效展示。完整检查方法及真实 Codex Work 验收状态见 [验证指南](docs/validation.md)。

## 开始自己的研究

1. 有仓库访问权限后，使用 GitHub 的 **Use this template** 创建自己的仓库，克隆到本地，在 Codex 中打开。
2. 准备 Git、Codex 和 [uv](https://docs.astral.sh/uv/getting-started/installation/)，在仓库根目录执行一次 `uv sync`。
3. 告诉 Codex 你的研究目的，例如：

```text
我想研究团队知识交接的方法，并准备一个面向新同事的 10 分钟分享。
请先确定研究范围和完成标准，再开始整理材料。
```

根目录初始没有课题知识。Agent 会按仓库约定初始化；普通问答无需建立完整交付目标，也无需你手写元数据。

## 在这些时刻使用

| 场景 | 可以直接说 |
| --- | --- |
| 多轮调研需要接续 | “继续上次研究，先告诉我哪些已确定、哪些仍是假设。” |
| 同一研究服务不同受众 | “保留技术报告，再做一版面向非专业同事的分享。” |
| 看完样稿想口述修改 | “这一段太技术化，保留风险说明，先不讨论成本。” |
| 准备结束本轮工作 | “生成简短交接，保留当前决定和下一步。” |
| 决定沉淀本轮知识 | “把这轮整理成一份有依据的变更摘要，供我审阅。” |

“进度已保存”表示文件留在本地；“知识已入库”表示具体变化经你确认并完成 Git 提交。接受保存一条假设，仍会保留它的假设身份。

## 为什么这样设计

**深模块，减轻用户负担：小入口承接意图，内部集中处理组织与检查。**

| 由谁承担 | 职责 |
| --- | --- |
| 你 | 研究目的、实质取舍，以及具体知识变化的接受 |
| Agent | 理解材料、判断证据、整理交接、写作与整体复核 |
| 脚本 | 分配 ID、检查引用与依赖变化、执行受控提交 |

长期知识共同保存，任务和交付按需建立。交接摘要指向当前状态和原文，不复制一套完整知识库。确定性检查集中在工具中，四个 Skill 复用同一工作流。

文件使用 Markdown 与结构化元数据，Git 保存版本；没有常驻服务或数据库。想深入时再看 [架构与边界](docs/architecture.md)、[工作流与命令](docs/workflow.md)、[字段契约](schemas/objects.yaml) 和 [领域术语](CONTEXT.md)。

## 有哪些证据，哪些仍需验证

2026-09-10 的本地检查记录为 **40 项测试通过**，覆盖引用、审阅范围、交接隔离、原文可用性和依赖变化等行为。测试与合成材料随仓库提供，检查命令见 [验证指南](docs/validation.md)。

真实 Codex Work 新任务接续与真实领域知识接受后的完整研究闭环仍待验收。文件协议也不能保证平台不注入整段历史；原文快照默认仅保存在本地，跨设备不会自动同步。

## 分享你的使用场景

介绍这个项目时，可以引用顶部的一句话定位，再配上交接案例中的一个具体问题，例如“怎样防止被否定的方案在下一次研究中重新出现”。读者可以顺着原 Chat、交接和样稿自行检查，再尝试自己的课题。

反馈或分享实践时，最有用的是三个片段：**你想完成什么、给了哪句指令、实际发生了什么**。附上可复现的最小例子与预期差异，能帮助项目改进。分享前移除真实研究中的敏感内容。

目前按私有模板阶段使用，公开发布与开源许可尚未确定。
